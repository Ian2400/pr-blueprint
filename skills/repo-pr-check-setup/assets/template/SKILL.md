# {{REPO}} PR Check

You run the final check a developer does before submitting a pull request to
{{REPO}}. The developer should come out of it with a branch whose clear-cut bugs
are fixed and tracked as issues, every judgment call decided by them, every
remaining concern written down for reviewers, and a draft PR whose description tells
reviewers what the change touches and what the author decided.

## Modes

| Invocation | Does |
|---|---|
| `/{{LABEL}}` (or any trigger phrase) | The three-phase check below |
| `/{{LABEL}} skip-security` (or "without the security scan") | The same check without the secrets/PII scan and the code vulnerability scan, for a small change where neither is worth its cost. Only when `config.json`'s `security.allow_skip` is true. See Phase 0, step 7. |
| `/{{LABEL}} learn <PR#>` | Reads reviewer comments on a submitted PR and proposes lessons. See `references/learning.md`. |
| `/{{LABEL}} consolidate` | For rules owners: turns open feedback issues into one rules-update PR. See `references/learning.md`. |
| `/{{LABEL}} check-vendor-updates` | Checks whether the vendored `cloudflare/security-audit-skill` copy (Phase 1.0a) is behind upstream, and reports what changed. Doesn't change anything. See "Mode: check-vendor-updates" below. |

The check has three phases. Do them in order and do not skip the approval gates.

| Phase | You do | Developer sees |
|---|---|---|
| 1. Review & Plan | Scan for secrets and personal data, run the code checks, review the diff, verify findings, triage, check existing issues | One plan summary and a go-ahead question |
| 2. Solve & Surface | Fix the lint groups the developer picks, file issues, launch fix agents, collect decisions | The lint report to pick from, Surface items one at a time, then the note list |
| 3. Confirm & Prep | Present each fix for approval, apply approved fixes, write the PR | Each fix, then the PR description, then the draft PR link |

## Showing things to the developer

The developer sees only the text of your messages. They don't see your tool calls,
tool results, files you write, command arguments (such as a `--body` or
`--body-file`), or the previews inside an AskUserQuestion. So whenever this skill
says to **show** something, or asks the developer to review, approve, or choose
based on it:

- **Put it in your message text, in full, before you ask.** A draft issue or PR
  description goes in a fenced markdown block exactly as it will be posted, title
  and labels included. A diff goes in a ```` ```diff ```` block. Findings, tables,
  and plans go in as text.
- **Then ask.** Never ask "does this look right?" about something that exists only
  in a file, a command, or a tool result.
- **After a revision, show it again:** the whole draft, or for a long draft with
  one small change, the changed part clearly marked.
- **What you post must match what you showed.** A file written for `--body-file` is
  fine, but it must contain exactly the approved text.

## Agents

Every agent this skill launches has a pinned model and effort. Pass both on every
Agent call (`model: "<model>"`, `effort: "<level>"`) so a run doesn't depend on the
session's own settings.

| Role | When | How many | Model | Effort |
|---|---|---|---|---|
| Security voter | Phase 1.0, when the scan finds anything | 1 | Opus 5.5 | medium |
| Review subagent | Phase 1.2, large changes only | One per file group | Opus 5.5 | high |
| Code vulnerability scan | Phase 1.0a | Self-orchestrating: the vendored skill spawns its own reconnaissance, hunter, critic, and verifier agents, capped by `config.json`'s `security.vuln_scan.budget` | Whatever the vendored skill's own prompts use (not ours to pin) | n/a |
| Category voter | Phase 1.4, every run with findings | 3 | Opus 5.5 | medium |
| Risk voter | Phase 1.4, every run with findings | 3 | Opus 5.5 | medium |
| Fix agent | Phase 2 | One per fix group, at most 6 at a time; three attempts per issue | `config.json`'s `fix_agents` — see "Fix agent tier" below | same |

Voters each judge **all** findings in one pass, so a run adds six voter agents no
matter how many findings it has.

### Fix agent tier

`config.json`'s `fix_agents` decides a fix agent's model and effort. This is a
repo setting (set at setup time, interview topic 14) — edit `config.json` directly
to change it; no engine upgrade needed.

- **`"tiering": "flat"`**: every fix agent uses `fix_agents.surfaced_tier` (model,
  effort), no matter the finding's risk.
- **`"tiering": "risk"`**: a Fix with AI finding uses the first entry in
  `fix_agents.tiers` (ordered low to high) whose `max_risk` is ≥ its risk. A
  grouped agent (2.1 step 2) takes its group's highest-risk tier. Anything
  surfaced to the developer and launched after "Fix now" (2.2, 2.2a) always uses
  `fix_agents.surfaced_tier`, regardless of risk — the developer already spent
  attention on it. A lint fix agent (Phase 2.0, not auto-fixable) has no risk
  score to key off and always uses `fix_agents.surfaced_tier`.

A stuck fix resumed with `SendMessage` (2.2a) keeps the tier its agent was
launched with; don't re-tier a running agent.

## The ledger

This is a long, multi-step flow, and the conversation may be compacted partway
through. Keep the state in a ledger file inside the repository's git directory so
nothing gets committed by accident:

`$(git rev-parse --git-common-dir)/{{LABEL}}/<branch>.json`, with every `/` in the
branch name replaced by `__` (so `feature/x` becomes `feature__x.json`).

```json

```

- **`risk`** is the median of the three risk voters' scores, from 1 (cosmetic) to 5
  (see "Risk scores" in `references/rubric.md` and "Risk priorities" in `rules.md`).
  Wherever this skill says "in risk order", it means highest first.
- **`votes`** keeps every voter's answer; **`split_vote`** is true when the category
  vote wasn't unanimous. **`needs_signoff`** is true for a Fix with AI finding with
  risk 4 or 5: its fix waits for the developer's sign-off.
- **`location`** is `{"file": ..., "line": ...}` for code. For findings that aren't
  in a file, use `{"pr_body": true}` or `{"commit": "<sha>"}`.
- **`why`** is required for every finding, including dropped ones, so a later run
  or a rules update can trace the decision. Cite rule IDs from `rules.md` where one
  applies.
- **`security`** on a finding is set only for `source: "security"`: the scan's id

  finding — see Phase 1.0a.

  `references/learning.md` for when and what to record.

Update it after every state change (an issue filed, an agent finished, a decision
made). If you resume and the ledger exists, read it and pick up where it says
instead of starting over. Tell the developer which phase you are resuming.

## Phase 0 — Set up

1. **Right repository.** Compare `git remote get-url origin` with `config.json`'s
   `host` and `repo`. If they don't match, stop: this skill's rules are for
   {{REPO}} only.
2. **Branch and base.** Find the current branch and the base branch: the remote's
   default branch (`git remote show origin`, `HEAD branch`), unless the developer
   names another. Refuse to run on the base branch itself; ask them to create a
   feature branch first.
3. **Clean tree.** If `git status --porcelain` shows uncommitted changes, ask the
   developer to commit or stash them. Fix commits are cherry-picked onto this branch
   later, and uncommitted work would get in the way.
4. **GitHub access.** Run `gh auth status --hostname <host>` and check that
   `gh repo view <host>/<repo>` works. If `gh` cannot reach it, stop and tell the
   developer how to authenticate (`gh auth login --hostname <host>`). Every issue
   and the PR depend on it.
   Also check that `config.json`'s `feedback_label` exists
   (`gh label list --search <label>`). If it doesn't, say once that lessons from
   this run can't be filed until a rules owner creates it, and continue.
5. **Existing PR.** Run `gh pr list --head <branch> --state open --json number,author,isDraft,body`.
   - If the developer already has an open PR for this branch, record it as
     `existing_pr` in the ledger. Phase 3 will update that PR instead of creating
     one, and its current description goes through the same checks as any finding.
   - If the open PR belongs to someone else, stop. This skill is for the author's
     own branch.
6. **Worktrees on Windows.** Phase 2 runs each fix in its own git worktree, and the
   worktree path is longer than the checkout's own path. On Windows, check
   `git config core.longpaths`. If it isn't `true` and the repo has long paths, ask
   the developer whether to run `git config core.longpaths true` for this repo.
   To check for long paths, see whether the longest tracked path
   (`git ls-files | awk '{ print length }' | sort -n | tail -1`) plus the repo
   root's length plus about 60 characters would exceed 260. Never change git config
   without asking. If they decline, create the worktrees yourself at a short path,
   for example `git worktree add C:/wt/<issue-number> -b <fix-branch> <head sha>`.
   Then launch the agents without `isolation` and tell each one its worktree path
   in the brief. Never let an agent work in the developer's own checkout.
7. **Skipping the security scan.** If the developer invoked the check with
   `skip-security`, or asked in their own words to skip the security scan, and
   `security.allow_skip` is true (treat a missing value as true): set the ledger's
   `security.status` **and** `security.vuln_scan.status` to `skipped`, with their
   reason in `skip_reason` (ask for a few words if they didn't give one, for
   example "one-line config change"), and say in one line: "Skipping the security
   scan: this branch won't be checked for secrets, personal data, or code
   vulnerabilities, and the PR will say so." Then skip the rest of this step, Phase
   1.0, Phase 1.0a, and the security gate in 3.5. If `allow_skip` is false, say the
   repo requires the scan and run it. Never skip it on your own initiative. If the
   developer's own words only mention one of the two (for example "skip the vuln
   scan, but still check for secrets"), skip only that one and run the other
   normally.

   **Security scan tools.** Otherwise, if `config.json`'s `security.enabled` is true, check
   `gitleaks version` (8.25 or later) and `python --version` (3.9 or later). If
   gitleaks is missing or old, give the install command for their OS
   (`winget install Gitleaks.Gitleaks`, `brew install gitleaks`, or
   https://github.com/gitleaks/gitleaks/releases) and ask: **Install it and continue**
   / **Continue without the security scan**. If they continue without it, set the
   ledger's `security.status` to `not_run` with the reason. The plan summary and the
   PR description then say the scan didn't run; never describe the branch as clean.
   This step is only for 1.0 (secrets/PII); 1.0a needs no extra tool beyond this
   session itself, so there's nothing to check here for it.
8. **Code check tools.** For each check in `config.json`'s `checks.items` that has
   files in this branch, check its command is installed (`ruff --version`,
   `sqlfluff --version`, `shellcheck --version`, or the tool's own). If CI pins a
   version (`mirrors_ci`), say when the local one differs. For a missing tool, give
   its install command and ask: **Install it and continue** / **Skip this check**. A
   skipped check is recorded and named in the plan summary and the PR description.
9. **Fetch** the base branch so the diff is current: `git fetch origin <base>`.
10. Create the ledger.
11. **The issue for this work.** An issue is the record of what was done and why, for
   the team and for any tool reading the history later. Settle it now, before
   reviewing, not at the end. How strict to be comes from `config.json`'s
   `work_issue.policy` (`existing_code` if it's missing):

   | Policy | An issue is |
   |---|---|
   | `always` | required for every PR |
   | `existing_code` | required when the PR changes existing production code; optional for new work |
   | `optional` | offered, never required |
   | `off` | linked if one is found; never asked about |

   - **Find it.** Look for an issue number in the branch name (and the branch
     pattern `rules.md` gives, if any), in commit messages (`#123`, `[#123]`), and in
     an existing PR's body (`Closes #123`). Check that it's open (or that this PR is
     reopening the work) and that its title fits the diff. If it clearly does,
     record it as `work_issue` and say which issue you're using in one line. This
     applies under every policy.
   - **Decide whether one is required** (`existing_code` policy). The PR changes
     existing production code when the diff modifies or deletes a file that exists
     on the base branch, outside the exploratory areas in `canonical.md`. A PR that
     only adds new files (or only changes files this branch itself added) is new
     work. `rules.md` can add signals under "Issues" (for example, a branch prefix
     that always means a production change); follow them. If it's unclear, ask
     the developer which it is. Record `issue_required` in the ledger.
   - **Required and none found** (or the one found doesn't fit): ask with
     AskUserQuestion before anything else:
     - **Create one now** (first, as the recommendation). Draft it from the branch
       name, commit messages, and a quick read of the diff, using the "Work issue"
       template in `references/writing-findings.md` and the labels `rules.md` says
       to use. If the security scan is on, run Phase 1.0 first and leave the files
       it flags out of what you read; the issue never quotes them. Ask the developer only what the code can't show: who asked for the
       work and why (a client request, a bug report, planned work). Write the full
       draft in your message (title, labels, and body in a markdown block, exactly
       as it will be filed), then ask them to approve or change it. Revise until
       they approve, then file that exact text with `gh issue create` and record its
       number.
     - **Use an existing issue.** Offer up to three likely matches from a search of
       open issues for the project area and the branch's key words, plus "a
       different number" in the Other box. Show the one they pick, and confirm it
       describes this work.

     There's no "skip" option. If the developer says in their own words that this
     PR shouldn't have an issue, accept it, record their reason as a lesson (see
     `references/learning.md`), and say in the PR's Summary "No linked issue:
     <their reason>". Repos that allow exceptions list them in `rules.md` under
     "Issues"; follow those without asking.
   - **Optional and none found** (new work under `existing_code`, or the `optional`
     policy): mention it once and ask: **Create one now** / **Use an existing
     issue** / **No issue needed**. "No issue needed" is a normal answer, not a
     lesson; the Summary then has no closing line.
   - **`off`:** don't ask.
12. **Vendor update check (throttled, never blocking).** Skip this if
    `security.vuln_scan.enabled` is false. Read
    `$(git rev-parse --git-common-dir)/{{LABEL}}/vendor-check.json`
    (`{"last_checked": "YYYY-MM-DD", "up_to_date": bool, "ahead_by": n,
    "compare_url": "..."}`). If it's missing or `last_checked` is 14+ days ago,
    run:
    ```bash
    python .claude/skills/{{LABEL}}/assets/security/check_vendor_update.py \
      --vendor-file .claude/skills/{{LABEL}}/assets/security/security-audit-skill/VENDOR.json
    ```
    and write the result (plus today's date) back to that file. Exit code 2
    (couldn't check — offline, API error) is not an error worth mentioning; just
    don't update `last_checked`, so it retries next run. If the result (fresh or
    cached) says an update is available, say one line: "`cloudflare/security-audit-skill`
    is N commits behind upstream — run `/{{LABEL}} check-vendor-updates` for
    details." Never block Phase 0 on this either way.

## Phase 1 — Review & Plan (internal)

Nothing in this phase goes to GitHub, and you show the developer nothing until the
plan summary at the end.

### 1.0 Secrets & PII scan

Run this first, before you read the diff: reading a diff that holds a password puts
the password into this conversation. Skip it only if `security.enabled` is false or
Phase 0 recorded `not_run` or `skipped`.

```bash
python .claude/skills/{{LABEL}}/assets/security/scan_branch.py --repo . \
  --base <merge base of origin/<base> and HEAD> --out <ledger dir>/security.json \
  [--patterns .claude/skills/{{LABEL}}/<security.patterns>]
```

It scans **every commit** on the branch, not only the final diff: a password added in
one commit and deleted in the next still ships in the branch's history. It looks for:

- secrets: gitleaks, with extra rules for connection strings, URL passwords, SQL
  roles and SAS `pw=`; also credentials typed into notebooks and Office documents;
- student data and other personal identifiers: PUIDs, SSNs, IDs next to grades or
  health data, in code, data files, spreadsheets, Word, PowerPoint and notebooks;
- key, credential, `.env` and data files the branch adds;
- what merge commits add while resolving conflicts, and the commit messages
  (`file` is `(commit message)` for those).

It can't read images (including notebooks' image outputs) or Git LFS objects, and
lists them under `not_inspected`.

It writes masked values only. Exit code 0 is clean, 1 is findings, and 2 means it
couldn't run: relay the error and treat the branch as not scanned, never as clean.

**Never look at a flagged spot directly.** Don't `cat`, Read, or `git show` a file the
report names, and leave it out of the diff in 1.1
(`git diff origin/<base>...HEAD -- . ':(exclude)<path>'`). When you need context, use
`scan_branch.py --peek <file>:<line> [--commit <sha>]`, which masks values. Don't hand
those files to review subagents, voters (no snippets of them in the findings packet
or change groups), or fix agents. Never open data files, images or PDFs
the branch adds.

**Triage by two judges.** If the scan found anything, read `rules.md` first
(Principles, Risk priorities, and "Don't report", which names paths that hold fake
credentials or synthetic data on purpose). Then launch the **security voter**
(`assets/voter-briefs.md`, `model: "opus"`, `effort: "medium"`,
`run_in_background: true`) with the path to `security.json`, and go on with 1.1
while it works. Judge each finding yourself as well, from the report and `--peek`
only:

- **Dismiss** a secret only when it's a placeholder, a code reference, or a dummy
  value in a test fixture. `fixture_hint` is a hint, not a verdict: real passwords
  in `examples/` are common. A path in "Don't report" makes dismissal likely, not
  automatic.
- **Keep** everything else.

Before 1.4, tally: a finding is dismissed only when you **and** the voter dismiss it.
Record each dismissal and both reasons in the ledger's `security.dismissed`. Every
other finding becomes a `source: "security"` finding, with `security` set from the
report. These skip the category voters (1.4) and are always **Surface**. Their risk
is the higher of the voter's score (which follows Risk priorities) and this floor:

| Kind | Risk floor |
|---|---|
| A secret that looks real, a key or credential file, high-severity personal data | 5 |
| Medium-severity personal data | 4 |
| A data file added with no identifiers found, or one the scan couldn't read | 3 |

Low-severity personal data (a few emails or IPs in code) is only counted.
**`not_inspected`** files become one Surface item, risk 3, that lists them: a person
has to look at each image, notebook output and LFS file for screenshots of data or
extracts. Never open them yourself. If the voter fails twice, keep every finding
(nothing is dismissed) and say so in the plan summary.

Set `security.status` to `clean` or `findings`.

### 1.0a Code vulnerability scan

This is a separate concern from 1.0: 1.0 catches secrets and personal data, this
step hunts for vulnerabilities in the code itself (auth bypass, injection, unsafe
deserialization, SSRF, and the like). Skip it if `config.json`'s
`security.vuln_scan.enabled` is false; record `security.vuln_scan.status` as
`skipped` with the reason.

Load `assets/security/security-audit-skill/SKILL.md` — a vendored copy of
[cloudflare/security-audit-skill](https://github.com/cloudflare/security-audit-skill)
(see its `VENDORED.md`) — and follow it as its own instructions govern **you** as
its "parent" for this step; this skill's own instructions resume at 1.0b. Run its
**full audit workflow**, scoped:

- **Scope.** A scoped run: in-scope paths are the files this branch adds or
  modifies (`security.vuln_scan.scope`, default `changed_files`). Read its
  "Run profiles and scope" section before seeding ledger units; everything outside
  those paths is `out_of_scope`, never `covered`.
- **Profile and budget.** `security.vuln_scan.profile` (default `quick`) and
  `security.vuln_scan.budget` (default 20, an agent-invocation cap per its "Cost
  budget" section). If the budget can't fund its reserved reconnaissance and
  critic calls, it reports `run_status: "incomplete"` on its own — relay that
  plainly, never as a clean scan.
- **Output directory.** `<ledger dir>/vuln-scan/` (inside the git directory, so
  nothing it writes can be committed by accident). Record this as
  `security.vuln_scan.run_dir`.
- **Exclusions.** Leave out anything 1.0 flagged and not yet dismissed, the same
  way 1.1 does, so a hunter never reads a live secret.
- **Sandboxing.** Follow its "Universal execution safety" section exactly — no
  network, no fetched dependencies, only existing local tooling. If this
  environment can't give every control it lists, don't execute target code for
  this step: let it fall back to source-only review and say so.

When it reaches a terminal state, read its `findings.json`. For each `confirmed`
record, add one candidate to this skill's own findings packet (1.4) with
`source: "vuln_scan"`, the vendored skill's fingerprint and severity in the
`vuln_scan` field, and its evidence and fix as the finding's body — then put it
through 1.3 (verify) and 1.4 (vote) like any review finding; its own severity is a
hint for the risk voters, not a substitute for their vote. For each
`needs_validation` record, fold it into this run the same way `needs_check` works
in 1.3: a candidate whose category and risk still get voted, but which becomes
Surface regardless of the vote (1.4's post-vote overrides), stating the vendored
skill's missing fact. Never put a `rejected` record into the packet.

Set `security.vuln_scan.status` to `clean` (no `confirmed` or `needs_validation`
records) or `findings`, and record the counts.

### 1.0b Code checks

Run the repo's linters on the files this branch changes. Read
`references/checks.md` the first time in a run.

```bash
python .claude/skills/{{LABEL}}/assets/checks/run_checks.py --repo . \
  --base <merge base> --config .claude/skills/{{LABEL}}/config.json --out <ledger dir>/checks.json
```

It runs every check in `config.json`'s `checks.items` (ruff, sqlfluff, shellcheck,
and whatever else the team added) with the repo's own tool configs, the ones CI
reads, and marks each finding as on a line this branch changed or elsewhere in a
file it touched. Exit code 2 means a check couldn't run: name it in the plan
summary, never call that check clean. Linter findings don't go through review,
voting, or issues: Phase 2.0 handles them. In 1.2, don't report anything a check
in the report already covers (same rule, same line).

### 1.1 Gather the change

- `git diff origin/<base>...HEAD` for the change, plus `--stat` (excluding files the
  security scan flagged).
- `git log origin/<base>..HEAD` for the commit messages; they often explain intent.
- Read the full current version of each changed file, not just the hunks. Many of
  the findings that matter come from how new code interacts with code outside the
  diff.
- Read `rules.md`, `examples.md`, any README in the changed directories, and any
  docs the rules point to (for example a connection library's README, fetched the
  way the rule says).

### 1.2 Review

Follow `references/review-checklist.md` and the review focus in `rules.md`. Find
every real problem; there is no cap on the number of findings. Triage, not the
review, decides what the developer sees.

For a large change, split the changed files into groups by directory or concern. A
change is large when it has more than about 1,500 **added** lines, or more than 15
files that were added or modified. Deleted lines and deleted files don't count,
because removed code needs little review. Give each group to a subagent
(`model: "opus"`, `effort: "high"`) with the checklist, `rules.md`, and the instruction to return candidate findings
as JSON (`file`, `line`, `problem`, `failure_scenario`, `suggested_fix`). Review
small changes yourself.

### 1.2a Duplication check

The goal is to stop the repository growing several slightly different ways of
doing the same thing. Read `canonical.md`, then for **every new function, class,
SQL function, or view** the PR adds (and every one a fix agent adds later):

1. **Search for existing versions.** By name (and close variants), and by what it
   computes: the libraries and operations at its core (for example `corr`,
   `pearsonr`, a logging handler setup, a date-bucketing expression). Search the
   whole repository with `git grep`, not just the changed directories.
2. **Decide what it is:**
   - **Matches a `canonical` entry:** it re-implements something the repo already
     has one way to do. A finding: Fix with AI, "use `<canonical>`".
   - **Matches an `undecided` entry, or existing code with no entry:** a finding:
     Surface, asking which version is canonical, with the options "Use `<existing>`"
     / "Keep the new one; it should be canonical" / "They're different: <how>". The
     first two answers are lessons that propose a `canonical.md` entry.
   - **A modified copy** of an existing function (same core, small changes): the
     same as above, and say exactly what differs. Small differences are the risk.
   - **Nothing similar:** not a finding.
3. **Exploratory areas.** If the new code is in a directory `canonical.md` lists as
   exploratory, any of the above is at most a Note.

Mark these findings `duplicates: {"existing": "<path or object>", "status":
"canonical|undecided|none"}`. They go through the vote like any other finding;
their risk is adjusted after (1.4).

### 1.3 Verify

Before triaging, re-check every candidate against the actual code at `HEAD`. Drop
any candidate you can show is wrong, or can't tie to specific lines.

- **Needs checking.** Some candidates hinge on something you can't see from the
  repository: whether a column exists, what a table holds, how a server is
  configured. If the failure is concrete *when* that fact holds, keep the
  candidate. Set `needs_check: true` and state the fact to confirm; it becomes a
  Surface item after the vote. Phrase it as a question the developer can answer
  from what they know. Never connect to a database or production system to find out.
- **Outside this PR.** If the problem is in code this branch doesn't change (even
  code it newly calls), it doesn't go into this PR's findings. Record it in
  `outside_scope` with location and one line. Phase 3 offers to file these as
  separate issues, so they aren't lost and don't bloat this PR.
- **Existing code that breaks a rule.** If code this branch changes or newly calls
  predates a rule in `rules.md` and violates it, the rule still wins, but the
  developer didn't write the violation. Never drop it and never fix it silently:
  set `predates_rule: true`; after the vote it becomes a Surface item that says
  plainly "this predates the rule", with the options "Fix it in this PR" / "File an
  issue for later". This is common while a
  codebase is first brought in line with its rules.

For each candidate that survives, record:

- **Impact:** does the affected code path actually run in what this branch delivers?
  A real bug in a value nothing reads is still worth fixing, but the finding must
  say so.
- **Edge case:** is this a rare input or circumstance? If so, mark `edge_case: true`
  and say how rare.

### 1.4 Triage by vote

Categories and risk are decided by two independent panels of three agents, not by
you alone. You prepare the findings; the voters judge them.

1. **Write the findings packet** to the ledger directory (`findings-packet.json`):
   for each verified finding, its `id`, title, location (and other locations), body,
   failure scenario, impact, edge-case label, `needs_check` fact, `predates_rule`,
   and a code snippet of up to 15 lines. Also list the PR's **change groups**: the
   diff split by what it touches (one function, one table's DDL, one pipeline
   script, one config), each with an `id` (`C1`, `C2`...), the files and commits,
   and a one-line summary. Leave out your own view of any category or risk, so the
   voters aren't anchored on it, including the vendored skill's own severity for a
   1.0a candidate. Security findings from 1.0 aren't in the packet; they're already
   decided. 1.0a's `confirmed` and `needs_validation` candidates are in the packet.
2. **Launch six voters at once**, in one message, each with `model: "opus"` and
   `effort: "medium"`, from `assets/voter-briefs.md`: three **category voters** and
   three **risk voters**. Each voter works alone, reads the code it needs, and
   returns JSON for every finding in the packet; risk voters also score every change
   group. Wait for all six.
3. **Tally the category.** Two or three matching votes win. A three-way split
   becomes **Surface**. Mark any non-unanimous result `split_vote: true`. Write the
   winning voters' shared reason into `why`.
4. **Tally the risk.** `risk` is the median of the three scores, for findings and
   change groups alike. Keep the risk voter's reason that matches the median as
   `risk_reason`. Change groups at 4 or 5 get a Revert plan entry in Phase 3.4; if
   the code already shows something there can't be undone (see `surfaces.md`'s "Can't
   be undone"), raise that group's risk by one, up to 5, and list it in
   `irreversible`.
5. **Combine them.**
   - Fix with AI and risk 4 or 5: stays Fix with AI with `needs_signoff: true`. Its
     issue is filed at the go-ahead, but its fix waits for the developer's sign-off
     in Phase 2.2.
   - Note and risk 4 or 5: becomes **Surface**. Something that risky is a decision,
     not a footnote.
   - Dropped stays dropped at any risk. Record the risk anyway; a high-risk drop is
     worth a second look when lessons are reviewed.
6. **Duplication raises risk.** For a finding with `duplicates`, add one to the
   voted risk (up to 5), and make it at least 4 when the duplicated logic falls under
   one of `rules.md`'s Risk priorities: two slightly different versions of
   high-stakes logic drift apart silently. Not in exploratory areas.
7. **Then apply the situations below and the existing-issue check (1.5)**, which can
   still move a finding to Surface. They never lower a finding's risk.

If a voter fails or returns findings it was not given, re-run that one voter once.
If it fails again, tally the two you have (a tie becomes Surface) and say so in the
plan summary.

After the vote, these situations override the voted category (never the risk):

- **Needs checking** or **predates a rule** (from 1.3): Surface, whatever the vote,
  unless the voters dropped it as wrong.
- **The PR deliberately departs from a rule** and explains it (in a comment, the
  commit message, or the PR body): Surface, whatever the vote, with two options:
  change the code to follow the rule, or keep it and propose amending the rule.
  Either answer is useful: the second becomes a lesson (`references/learning.md`).
- **The standard is unclear.** The rules point to a standard (a library's README,
  say) that doesn't settle whether this code complies. Make it a Note (Surface if
  its risk is 4 or 5), and add one
  line to `unclear_standards` saying exactly what the documentation leaves open.
- **The PR description itself** (for a PR that's already open) has placeholders,
  stale numbers, or missing links. Make it a Note with `location: {"pr_body": true}`.
  Phase 3 rewrites the description anyway, so these get fixed there.

### 1.5 Check for existing issues

**Gather candidates once, then match.** Searches that use a finding's exact wording
usually return nothing, so build a candidate list first:

- Issues referenced in the branch name, commit messages, or an existing PR body
  (`#1234`).
- `gh issue list --state open --search "<project or area name>" --limit 30`, using
  the changed directories' project names, plus one search per distinctive name a
  finding involves (function, table, script).
- Any tracking issues `rules.md` names.
- Read the body of each candidate that looks related. A tracking issue with a
  checklist counts item by item: each checkbox is its own candidate, and an item
  that is checked off, or marked as fixed on another branch, is no longer open.

Then classify each candidate against each finding:

- **Duplicate:** the issue (or one open checklist item) describes this specific
  problem. Set `existing_issue`. If the finding was Fix with AI or Surface, it
  becomes Surface, so the developer decides whether to fix it in this PR. A Note
  stays a Note, with "tracked in #N" added. Never file a duplicate.
- **Related:** same area or a broader goal, but not this problem. Add it to
  `related_issues` and keep the finding's category. The finding body and the
  PR's Known follow-ups section mention it as `Related #N`.

Separately, collect issues that **this PR itself resolves**: ones whose request the
diff carries out. Record them in `resolves_issues`. Phase 3.4 asks the developer
to confirm each one before writing `Fixes #N`.

### 1.5a PR types

`rules.md` may define **PR types** under "PR types": kinds of PR (for example ones
that change a model, or a schema migration) with how to recognize them, sections
their description must include, and sign-offs they need. If it defines none, skip
this step.

For each type, check whether this PR matches its detection rule, and record matches
in the ledger's `pr_types`. For a type that needs a sign-off, do what its rule
says:

- **Recorded** (an issue comment, a review): look for it there.
- **Ask:** ask the developer, once, with the other Phase 1 questions. Their answer
  is the record; don't ask them to write it anywhere.

A missing sign-off becomes a Surface item (risk from the rule, else 3) with the
options "I'll get it before review" (it then goes under Known follow-ups) and "This
PR isn't that type" (a lesson), plus "It's there: <where>" for a recorded sign-off.
Never record a sign-off on someone's behalf.

### 1.6 Plan summary

Write the findings in the voice described in `references/writing-findings.md`, then
show the developer one compact summary, using the template there. It shows:

- Counts per category. The headline total covers only what the developer will see
  (Fix + Surface + Note), and dropped findings get a separate line.
- The issue this work is tracked in (`work_issue`), or why there's none (new work
  with no issue needed, or the developer's reason).
- The security scan: commits scanned; items kept, dismissed (one line each, with the
  reason) and not inspected; or that it didn't run, or was skipped, and why.
- The code vulnerability scan: its profile, how many `confirmed` and
  `needs_validation` records it produced (now counted in Fix/Surface/Note below),
  or that it didn't run, was skipped, or came back `incomplete`, and why.
- Code checks: per check, findings on the developer's lines and elsewhere in touched
  files, how many are auto-fixable, and any check that didn't run. Say they're
  handled after the go-ahead.
- How many votes were split, and how many fixes need sign-off.
- The PR types it matches, if `rules.md` defines any, and any sign-off still missing.
- Duplication: how many new functions re-implement something that exists, and how
  many need a "which is canonical?" answer.
- The high-risk change groups that will get a Revert plan entry, one line each, with
  any that look irreversible marked.
- How many findings duplicate an existing issue, and any issues this PR appears to
  resolve.
- The Fix with AI list: one line each (risk, title, location), with fixes that need
  sign-off listed separately.
- Unclear standards and outside-this-PR problems, one line each, if there are any.
- One line saying that judgment calls and notes come next.

Then ask one question with AskUserQuestion: **file the N issues and start the M
low-risk fixes?** (Fixes that need sign-off get their issues filed now and wait for
Phase 2.2.)
Options:
- Start all.
- Let me look at or remove some first. Show the full body of any items they ask
  about, then move the ones they name to Surface or Dropped as they say (each move
  is a lesson).
- Stop here. Filing issues is visible to the whole team, so don't file anything
  until the developer answers.

## Phase 2 — Solve & Surface

### 2.0 Code checks: report, then the developer picks

Before any fix agent starts (they start from the branch as it is after these
commits), follow `references/checks.md`:

1. **Report first.** Show the groups from `checks.json`, one line per check and
   rule: count on the developer's lines, count elsewhere in touched files, and
   whether it's auto-fixable.
2. **Scope.** Ask whether to include "elsewhere in touched files" this run. The
   default is `checks.scope`; record the answer as `checks.scope_chosen`.
3. **Pick.** The developer selects which groups to fix (AskUserQuestion
   multi-select with four or fewer groups, numbers in chat otherwise). Nothing is
   fixed without being picked.
4. **Fix in small commits**, one per picked group:
   - auto-fixable: `run_checks.py --fix <check>:<rule> --files <files>`; show the diff;
     commit `Lint: <check> <rule> (<n> files)` when the developer approves it;
   - not auto-fixable: one fix agent per group (`assets/fix-agent-brief.md`, with
     the group's findings in place of an issue). Its commit goes through 3.2 like
     any fix. No GitHub issue is filed for lint.
5. **Unpicked** groups on the developer's lines go into the PR description's
   `code_checks` section (or `reviewer_notes`) with the reason they gave. A group
   left unpicked in this run is a lesson only if they say why it's wrong for the
   team (`references/learning.md`).

Record `checks.selected` and `checks.skipped` in the ledger, and the new `HEAD`.

### 2.1 File issues and launch fix agents

For each approved Fix with AI finding (file issues for all of them; launch agents
only for those without `needs_signoff`):

1. **File the issue** with `gh issue create`, using the title and body format in
   `references/writing-findings.md` and the labels `rules.md` says to use. Add a
   label only if it already exists in the repo (`gh label list`); never create
   labels. Record the issue number.
2. **Group before launching.** Findings that touch the same file within about 30
   lines of each other go to the same agent, so two worktrees never rewrite the same
   hunk. Each finding still gets its own issue and its own commit.
3. **Launch one agent per group** with the Agent tool: `model` and `effort` from
   the group's tier ("Fix agent tier" under Agents, above — the group's
   highest-risk finding sets the tier), `isolation: "worktree"`,
   `run_in_background: true`. If Phase 0 set up short-path worktrees instead, leave
   out `isolation` and give each agent its worktree path in the brief. Fill
   `assets/fix-agent-brief.md` for it. Start every worktree from the developer's
   current `HEAD` (the brief tells the agent to verify this). Run at most 6 agents
   at once; queue the rest and launch each as another finishes.

Record each agent, worktree, and branch in the ledger. Don't wait for the agents
before moving on to 2.2.

### 2.2 Sign-offs, then Surface to Developer, one at a time

While the agents work, take the **sign-off items first**, highest risk first. For
each, show the finding, its risk score with `risk_reason`, the votes, and the exact
fix planned. Ask: **Sign off: fix as planned** / **Fix it differently** (their
approach in the Other box, quoted into the agent's brief) / **Make it a decision
instead** (treat it as Surface) / **Not now: leave the issue open**. Launch a fix
agent only after a sign-off or a changed approach.

Next, the **security items**, before any other Surface item. Show the masked line,
`file:line`, the kind, whether its commit is pushed, and whether the value is still
in `HEAD`. Never file a GitHub issue for one, and never give one to a fix agent. The
options depend on the case:

- **Secret or credential file, not pushed:** "Remove it and rewrite the unpushed
  commits" / "It's a dummy value" (ask for the reason; a lesson). To remove it, the
  developer replaces the value with the repo's standard way to load credentials (see
  `rules.md`), or you `git rm --cached` a credential file and add it to
  `.gitignore`. Then, with their go-ahead, `git reset --soft <the last pushed commit,
  or the merge base>` and make one new commit with a message they approve, so the
  value never reaches the server.
- **Secret or credential file, already pushed:** say plainly that everyone who can
  read the repository can see it, so it must be **rotated**; removing it from the
  code doesn't undo that. "I've rotated it (or will now): remove it from the code" /
  "It's a dummy value". Rewriting pushed history is the developer's call; never
  force-push.
- **In a commit message:** the same pushed / not-pushed split. Not pushed: the
  rewrite above, with a new message that leaves it out. Pushed: rotate it.
- **Files nobody could inspect:** "I've looked: no personal data" / "Remove them"
  (handled like a data file below).
- **Personal data or a data file:** "Remove the file from the branch" (`git rm
  --cached`, a `.gitignore` entry, and the rewrite above if nothing is pushed) /
  "It's synthetic or approved data" (ask who approved it; a lesson). If it's pushed,
  tell them to inform the data steward, and that the `repo-security-audit` skill
  does the full assessment.

Change a line that holds a secret only by line number, with a command that never
prints the line, or leave the edit to the developer and show them where. After any
change, re-run the scan (1.0) and confirm the item is gone.

Then take the other Surface items in risk order. For each one,
show the finding (title, `file:line`, the problem in two or three sentences, the
failure scenario, impact, edge-case label, risk, and "split vote" if it was) and ask
with AskUserQuestion. The options
depend on the finding:

- Several valid fixes: one option per concrete fix (name the fix, not "Option A";
  put your recommendation first, marked Recommended).
- One fix, but it depends on context: "Fix it as suggested" / "It's intentional,
  drop it" (ask for the reason in the Other box).
- Linked to an existing issue `#N`: "Fix now (closes #N)" / "Leave it for #N".
- Needs checking: "Confirmed, it's a problem: fix it" (then the fix options) /
  "Not a problem here" (ask for the fact that rules it out, if they'll give it).
- Always available: "Not now: file an issue for later".

The developer can always answer in their own words. Treat a written answer as the
decision and restate it in one line before acting on it.

After each answer:

- **Fix now:** file an issue if there is no existing one (put the developer's
  decision in the body under "Decision"), then launch a fix agent with
  `config.json`'s `fix_agents.surfaced_tier` (every fix that reached this step was
  surfaced to the developer, so it's always this tier regardless of its risk
  score) with the decision quoted in the brief.
- **Fix now, existing issue:** don't file anything. Launch the agent
  (`fix_agents.surfaced_tier`, same reason) against `#N`, and later use `Fixes #N`
  in the PR.
- **Not now:** file an issue if one doesn't exist, with `config.json`'s
  `deferred_label` if it has one. The PR description lists it under "Known
  follow-ups".
- **Intentional / drop:** mark it dropped with the developer's reason, and record a
  lesson.

When an agent finishes during this step, don't interrupt the current question. Note
the result in the ledger and mention it briefly after the developer answers.

### 2.2a Stuck fixes go back to the developer

A fix agent stops after three failed attempts on an issue, or sooner if the fix
can't be done as described, and reports `stuck` (see `assets/fix-agent-brief.md`).
Treat that as a sign the finding was harder than its category said. Record the
attempts in the ledger, set the status to `stuck`, and put it in the question queue
right after the question the developer is answering now.

Show the finding, its risk, what each attempt changed and why it failed, the
agent's diagnosis, and the options it sees. Ask:

- **Here's how to fix it:** the developer's guidance in the Other box. Send it to
  the same agent with SendMessage, quoted, with a fresh three attempts. Increase
  `escalations`.
- **I'll fix it myself:** remove the agent's worktree, leave the issue open, and
  check `git log` before Phase 3 for their commit.
- **Not now: leave the issue open.** Add a comment to the issue with the attempts
  and diagnosis (no secrets, no credential contents), and list it under "Known
  follow-ups".
- **It's not worth fixing:** close the issue as not planned with their reason.

If the same issue gets stuck a second time after guidance, don't offer another round
with the agent: offer only the last three options. Every stuck fix is a lesson (see
`references/learning.md`).

### 2.3 Note to Developer

When every Surface item is answered, show the notes as one numbered list: title,
`file:line`, and one sentence each. Tell the developer:

- They can remove any note they think is wrong or trivial (reply with the numbers),
  fix any themselves now while the agents finish (and commit before Phase 3), or
  leave them.
- Notes they keep and don't fix go into the PR description under "Notes for
  reviewers".

With four or fewer notes, use an AskUserQuestion multi-select ("Remove which?").
With more, ask for the numbers in chat. Mark each note `removed` or `kept`; a note
removed as wrong is a lesson. Before Phase 3, check `git log` for commits the
developer added. If a commit fixes a kept note, ask whether to mark it `fixed by
developer`.

## Phase 3 — Confirm Fixes & Prep PR Submission

### 3.1 Wait for the agents

Phase 3 starts when every fix agent has reported and every stuck fix has a decision
(2.2a). If some are still running, tell the developer which ones and wait for their
completion notifications. Never poll, and never guess at a result.

### 3.2 Approve each fix

For each fixed finding, in risk order, show:

- The issue (`#N`, title), its risk, and the one-line summary of the fix. For a
  signed-off fix, also what the developer signed off on, so they can check the fix
  matches it.
- Any new helper the agent added (`new_helpers` in its report), with what it
  searched for and why nothing existing fit. Run the duplication check (1.2a) on
  it; a match turns the approval into a request for changes.
- `git show --stat <commit>` and the changed hunks, pasted into your message in a
  ```` ```diff ```` block (trim hunks over about 60 lines to their essential parts
  and say that you trimmed them). The output of your own `git show` call isn't
  visible to the developer.
- What the agent ran to verify the fix and what that showed. If it could not
  verify, say so plainly.

Ask with AskUserQuestion: **Approve** / **Request changes** / **Reject**.

- **Request changes:** take the developer's reasoning and send it to the same agent
  with SendMessage, so it keeps its context. Then show the revised commit and ask
  again. Repeat until approved or rejected. If the reasoning states a convention
  ("we always X"), record a lesson.
- **Reject:** ask whether to close the issue as not planned (`gh issue close <N>
  --reason "not planned" --comment "<their reason>"`) or leave it open as a
  follow-up. Record a lesson.

### 3.3 Apply approved fixes

Cherry-pick the approved commits onto the developer's branch, in risk order:
`git cherry-pick <sha>`. If a cherry-pick conflicts:

- Resolve it yourself only when both sides' intent is clear and the result keeps
  both fixes. Then show the developer the resolution.
- Otherwise abort that cherry-pick (`git cherry-pick --abort`), tell the developer
  which two fixes collide, and ask how to proceed.

Then re-run the code checks (1.0b) and report anything the applied fixes
introduced on changed lines. Also run the repo's tests if it has them (a test
directory, `pytest.ini`, `pyproject.toml`, CI workflow steps) for the directories
the change touched. Report the results honestly, including failures.

Remove the fix worktrees once their commits are applied or rejected
(`git worktree remove <path>`, then `git branch -D <fix-branch>`).

### 3.4 Write the PR description

Read `references/pr-description.md` and `config.json`'s `pr_description`. If the PR
is already open, start from its current description and keep everything that's
still accurate. When there's a `work_issue`, the Summary links it with a closing
keyword (`Closes #N`) so merging closes it. Confirm each issue in `resolves_issues` with
the developer before writing `Fixes #N` for it. Add one line on the security scan: "Security scan: N
commits checked, nothing found", what was removed (kinds and counts, never values or
paths to data), that it didn't run, or "Security scan: skipped by the author
(<skip_reason>)". Add a second line on the vulnerability scan: "Vulnerability scan
(<profile>): nothing confirmed", the number fixed or surfaced, that it was
skipped, or that it came back `incomplete` with its reason — never silently
drop this line because 1.0a found nothing. If `config.json` lists the `security` section,
use that section; otherwise add the lines at the end of `testing` or `summary`. Fill
`code_checks` the same way if it's listed (or one line in `testing` if not). Draft
the description from the diff, then ask the
developer only what the code cannot tell you. Write the full draft in your
message, exactly as it will be posted (title, then the body in a markdown block),
and ask whether it's ready. Revise and show it again until they say it is. Never leave a required section blank: write "None in
this change" when that is true.

The description has three parts, for reviewers, for engineering, and for on call
(see `references/pr-description.md`). Add the sections any matched PR type requires.

**New helpers.** List every new helper a fix agent added under "Notes for
reviewers", one line each, so reviewers can judge whether it belongs in
`canonical.md`.

**Deploying this.** Every description's engineering part ends with it, whatever
`config.json`'s sections say. Read `references/deploy-plan.md` and `surfaces.md`,
then write every step this PR needs to go out, in order, with failure handling,
objects created and dropped, schedule, and environment. Ask the developer what the
code can't show (schedule times, hosts, steps already run) in the same batch as the
other description questions.

**Revert plan.** Every description ends with a Revert plan, whatever
`config.json`'s sections say. Read `references/revert-plan.md` and `surfaces.md`, then
write an entry for every change group at risk 4 or 5, including the commits of
high-risk fixes this run made. Fill each surface's steps from the code; ask the
developer only for what the code can't show (what's live in production, how a
deploy was done). If `surfaces.md` doesn't exist, write the code steps only in both
plans and say once that the repo has no change surfaces yet (re-running
`repo-pr-check-setup` adds them).

### 3.5 Open the draft PR

When the developer approves the description:

0. **Irreversible changes.** If any Revert plan entry lists something irreversible,
   show each one (what it is, what would be lost) and ask: **Acknowledge** /
   **Add a safety step first** (a backup or a renamed copy of the old version; a
   code change goes through the normal fix flow, then the plan is redone) / **Go
   back**. Record the developer's login in `acknowledged_by` for each acknowledged
   entry, in the ledger and the plan's block. Don't push until every irreversible
   item is acknowledged.
1. **Security gate** (not when the scan was `skipped`). Re-run the secrets/PII scan
   (1.0, not 1.0a — the vulnerability scan isn't re-run here) on the branch as it
   is now, and scan the approved description with `scan_branch.py --text <body
   file>`. If any item is neither dismissed nor resolved and `security.block_push`
   is true, don't push: show the items and go back to them. The developer can
   override only in their own words. Record it in `security.push_override` with
   their reason, make it a lesson, and name the kinds (never the values) in the PR
   description.
2. `git push -u origin <branch>`.
3. Write the body to a temporary file outside the repo. Then:
   - **No existing PR:** `gh pr create --draft --base <base> --title "<title>" --body-file <file>`.
   - **The developer's PR is already open:** `gh pr edit <N> --title "<title>" --body-file <file>`.
     Don't convert a ready PR back to draft unless the developer asks.
4. Give the developer the PR link. List the issues it will close and the issues
   left open as follow-ups.
5. Set the ledger phase to `done`.

### 3.6 Loose ends

- **Outside this PR:** if `outside_scope` has entries, list them and ask which to
  file as separate issues (check for duplicates first, as in 1.5).
- **Lessons:** follow "End of a run" in `references/learning.md`. Never edit
  `rules.md` on the developer's feature branch.
- Mention once that after reviewers comment, `/{{LABEL}} learn <PR#>` feeds their
  comments back into the rules.

## Guardrails

- **Never push or open the PR before the developer approves the description** and
  acknowledges every irreversible change in the Revert plan. Never mark the PR ready
  for review, and never merge anything.
- **Never file an issue before the Phase 1 go-ahead**, except the work issue in
  Phase 0, and only once the developer approves its draft. Never file a duplicate
  of an open issue.
- **When `work_issue.policy` requires an issue, the PR links one**, unless the
  developer gave a reason for none, which goes in the Summary.
- **No fix churns.** Three failed attempts per issue, then the developer decides
  (2.2a). Never let an agent try a fourth time on its own, and never relaunch a
  stuck fix with no new guidance.
- **No high-risk fix runs without sign-off.** A Fix with AI finding with risk 4 or 5
  waits for the developer in Phase 2.2.
- **Fix agents never push, never open PRs, and never touch the developer's branch.**
  They commit only on their own worktree branch.
- **One issue per fix, one commit per issue.** The commit subject starts with
  `Fix #N:`, so the history maps commits to issues. Lint fixes are the exception:
  no issue, one commit per picked group, subject `Lint: <check> <rule>`.
- **Never change a linter's config on the feature branch** (`pyproject.toml`'s
  `[tool.ruff]`, `.sqlfluff`, `.shellcheckrc` and the like). Those are team rules:
  propose changes as lessons.
- **Respect the principles in `rules.md` over generic best practice.** Never "fix"
  behavior a rule calls deliberate.
- **Only rules owners change the rules.** This skill proposes changes as feedback
  issues or a rules PR; `CODEOWNERS` decides who approves them.
- **Show before you ask.** Every draft, diff, or finding the developer is asked to
  approve or decide on is in your message text first, never only in a tool call or
  file (see "Showing things to the developer").
- **Say what you didn't verify.** If tests couldn't run or an agent couldn't
  reproduce a bug, the developer hears it before approving.
- **Credentials and personal data.** Never print, log, or put in an issue any
  secret, password, credential file contents, or personal identifiers you come
  across while reviewing. Describe the location instead, and read flagged spots only
  through `scan_branch.py --peek`.
- **Nothing the security scan flags reaches the server without the developer's
  say-so.** Phase 3.5 re-scans before every push, and a scan that couldn't run is
  never a pass. Only the developer can skip the scan, per run, where the repo allows
  it; a skipped scan is stated in the PR, never presented as clean.
